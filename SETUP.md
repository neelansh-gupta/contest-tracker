# Contest Tracker — setup (do this once)

This rebuild fixes both recurring pains from the old version:

1. **Google token expiry** — the old script used a user OAuth flow
   (`token.json`), and Google caps refresh tokens for unverified apps at
   7 days. Every week the token died and had to be regenerated by hand.
   Fix: a **service account** instead. Service account keys don't expire
   and never need re-consent.
2. **clist.by auth breaking** — the old script went down an OAuth path
   (client id/secret, "client credentials" grant) that clist.by's contest
   endpoint doesn't reliably support, and it kept 401ing whenever the
   secret got regenerated. Fix: clist.by's actual intended auth is much
   simpler — a plain `username` + `api_key` pair from your profile page.
   No token, no expiry, no regeneration unless you do it yourself.

Once you finish the steps below, the script needs **zero maintenance** —
no keys to rotate on any schedule.

---

## 1. Get your clist.by API key

1. Log in at https://clist.by/login/
2. While logged in, visit https://clist.by/api/v4/ (or your profile page) —
   your key is shown as `username:apikey`.
3. Save the `username` part and the `apikey` part separately — you'll need
   both.

That's it. No OAuth app, no client secret. This key is stable until you
manually regenerate it from your account settings.

---

## 2. Create a Google service account

1. Go to https://console.cloud.google.com/ and create (or reuse) a project.
2. Enable the **Google Calendar API** for that project
   (APIs & Services → Enable APIs and Services → search "Google Calendar API").
3. Go to **IAM & Admin → Service Accounts → Create Service Account**.
   Any name is fine (e.g. `contest-tracker`). No roles needed at the
   project level — access is granted via calendar sharing instead.
4. Open the new service account → **Keys → Add Key → Create new key → JSON**.
   This downloads a `.json` file — keep it, you'll paste its contents into
   a GitHub secret in step 4.

---

## 3. Share your calendar with the service account

1. Open the downloaded JSON file and copy the `client_email` value
   (looks like `contest-tracker@your-project.iam.gserviceaccount.com`).
2. In Google Calendar, go to the settings of the calendar you want events
   synced to → **Share with specific people** → add that email with
   **"Make changes to events"** permission.
3. Note the **Calendar ID** from the same settings page (for your primary
   calendar this is just your Gmail address; for a secondary calendar it's
   a long id ending in `@group.calendar.google.com`).

---

## 4. Add GitHub repo secrets

In your repo: **Settings → Secrets and variables → Actions → New repository secret**.

| Secret name | Value |
|---|---|
| `CLIST_USERNAME` | your clist.by username |
| `CLIST_API_KEY` | your clist.by api key |
| `GOOGLE_SERVICE_ACCOUNT` | the **entire contents** of the service account JSON file |
| `GOOGLE_CALENDAR_ID` | the calendar ID from step 3 |

---

## 5. Push the code and run it

Push `sync.py`, `requirements.txt`, and `.github/workflows/sync.yml` to a
repo. The workflow runs every 6 hours automatically, or trigger it once by
hand from the **Actions** tab → select the workflow → **Run workflow**.

To test locally first:

```bash
export CLIST_USERNAME=your_username
export CLIST_API_KEY=your_api_key
export GOOGLE_CALENDAR_ID=your_calendar_id
export GOOGLE_SERVICE_ACCOUNT_FILE=/path/to/service_account.json
python3 sync.py
```

---

## Why this stays working

- The service account credential has no expiry and needs no user consent
  step — that was the entire source of the weekly Google breakage.
- The clist.by key is the auth mechanism the API actually documents for
  scripts (plain key, not OAuth) — the OAuth path in the old version was
  a wrong turn, not a necessary complexity.
- The script only ever touches events it created itself (tagged via
  `extendedProperties`), so it's safe to point at a calendar you also use
  for other things.

The only time you'd ever need to touch a secret again is if you manually
revoke/regenerate the clist.by key or delete the service account — neither
of which happens on its own.
